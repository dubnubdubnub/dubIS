# dubIS — Codebase Guide

## Architecture

Desktop app: Python backend + vanilla JS/HTML/CSS frontend, served over HTTP. `app.pyw` spawns the `/v1` FastAPI server (`server/`) on a loopback port, then opens a pywebview window pointed at `splash.html`, which self-navigates to the app once the server answers `/v1/health` — the webview window is just a browser; the app is a client of its own `/v1` API (dogfooding), not a JS-bridge app. The old ~76-method pywebview bridge shrank to a ~9-method client shell (`client_shell.py`) for OS-only concerns (file dialogs, close-confirm, BOM-dirty tracking) that have no HTTP-y shape; everything else — data, mutations, push updates (SSE) — goes over `/v1`.

## Data Flow

CSV files are the source of truth. SQLite cache is a derived, deletable materialized view.

```
purchase_ledger.csv + adjustments.csv
        │
        ▼
  inventory_ops.py          (merge dupes → apply adjustments → categorize → sort)
        │
        ▼
  cache_db.py               (populate SQLite: parts + stock tables)
        │                   catch_up() replays only NEW adjustment rows since last checkpoint
        │                   full rebuild if purchase_ledger changes or cache missing
        ▼
  cache.db (SQLite)         (query_inventory() → list[InventoryItem] sent to JS)
        │
        ├── prices table    (populated by domain/pricing.py from events/price_observations.csv)
        ├── part_attributes (populated by domain/attributes.py from data/part_attributes.csv)
        └── generic_parts   (manual state durable in data/generic_parts.json; auto groups regenerated)
```

All inventory-mutating API methods (`adjust_part`, `import_purchases`, `consume_bom`) append to CSVs, then rebuild cache and return fresh `list[InventoryItem]`. The cache can be deleted at any time — it rebuilds on next `rebuild_inventory()`.

## Agent Tooling

Two custom MCP servers are configured in `.mcp.json` at the repo root, plus the inventory CLI. Inventory work goes through the CLI, not an MCP server — see the dubis CLI section below.

### devtools MCP (`tools/dev-tools-mcp/server.py`)

Efficiency tools that reduce token usage by eliminating redundant reads and providing smarter search:

| Tool | What it does |
|------|-------------|
| `symbol_search` | Jumps straight to a function/class/variable definition and returns its full body — no grep-then-read round trip |
| `block_grep` | Like grep but returns the entire enclosing function/block, not just the matching line — also skips the grep-then-read round trip |
| `event_trace` | Finds all emitters and listeners for a named EventBus event across the whole `js/` tree |
| `api_callers` | Finds every JS call site for a Python backend method, handling all calling conventions (string-keyed `api("name", ...)`, legacy `api.name()`, `pywebview.api.name()`) |
| `file_ops` | `mkdir`, `mv`, `cp`, `rm` — batch file operations within the project root |
| `line_edit` | Replace a line range by number (no old-text matching required) — use when you already have line numbers from Grep/Read |
| `multi_edit` | Apply multiple line-range replacements to one file in a single call (applied in reverse order so line numbers stay valid) |

**Worked examples for this repo's most common reverse-mapping tasks:**

```
# Every JS call site of a backend method (string-keyed bridge convention):
api_callers("adjust_part")

# Every emitter + listener for an event (replaces hand-reading the EventBus table):
event_trace("INVENTORY_UPDATED")
```

### ssh MCP (`tools/ssh-mcp/server.py`)

Remote access to the PnP machine and test runner over Tailscale — see `memory/reference_pnp_machine.md` and `memory/reference_ux430_testbox.md` for connection details.

### dubis CLI (`tools/dubis-cli/dubis.py`, launcher `scripts/dubis`)

Every `/v1` route as `dubis <resource> <verb>`, generated from `docs/openapi-v1.json` by `scripts/gen-cli.py` — an HTTP client of `/v1`, never a direct CSV/SQLite reader. Discovers a running server via `DUBIS_URL` → `<data_dir>/.v1_port` → `<data_dir>/.v1_uds` (all health-checked). It does **not** start one: `dubis serve` does that explicitly — `dubis serve --uds <path>` for the Unix-socket transport, which does not forward `--host`/`--port` because `python -m server` rejects the combination.

```bash
scripts/dubis serve                                              # start /v1 (everything else needs it)
# hot path — hand-written in tools/dubis-cli/curated.py, these are compositions, not routes
scripts/dubis search 100nF                                       # substring over lcsc/mpn/desc/mfr/package
scripts/dubis get C1000                                          # detail card: stock, prices, groups, history
scripts/dubis low-stock                                          # per-section thresholds from preferences
scripts/dubis spec-search capacitor 100nF --package 0402
scripts/dubis jlc library                                        # paired JLC accounts
scripts/dubis jlc library 12625901A                              # that account's private library
# generated surface — every /v1 route
scripts/dubis parts adjust C1000 --adj-type add --quantity 50    # --source defaults to "cli"
scripts/dubis parts adjust C1000 --adj-type add --quantity 50 --dry-run
scripts/dubis schema --json                                      # all 90 generated commands + params
```

Path params are positional, everything else is a flag; global flags work before or after the subcommand. Exit codes: `2` bad usage, `3` server or precheck error, `4` no server found. Mutations are tagged `--source` so `dubis adjustments rollback-source <name>` undoes a session.

`parts adjust --adj-type add|remove` against a part that does not exist exits 3 rather than letting `/v1` silently no-op it; `set` creates parts on purpose and is exempt. A part key that matches nothing exits 3 everywhere, so a miss is never a silent success. `--dry-run` never contacts the server, so it will not catch an unknown key. Full detail lives in the generated `.claude/skills/dubis-cli/SKILL.md`.

The nine hot-path commands (`status`, `search`, `get`, `spec-search`, `low-stock`, `prices`, `history`, `generic-groups`, `jlc`) are hand-written, not generated — they are compositions the OpenAPI spec cannot describe (`get` aggregates five routes, `search` filters client-side since no `/v1` search route exists). Add new ones to `tools/dubis-cli/curated.py`; the generated skill picks them up automatically.

## EventBus Flow

Events are centralized in `js/event-bus.js`. Store setters that emit are marked; unlisted setters do NOT emit.

| Event | Emitted by | Listened by |
|-------|-----------|-------------|
| `INVENTORY_LOADED` | store.js (`loadInventory`) | inv-events.js, bom-events.js, app-init.js |
| `INVENTORY_UPDATED` | store.js (`onInventoryUpdated`) | inv-events.js, bom-events.js, app-init.js, label-selection.js |
| `BOM_LOADED` | bom-panel.js | inv-events.js, app-init.js |
| `BOM_CLEARED` | bom-events.js | inv-events.js |
| `CONFIRMED_CHANGED` | store.js (`confirmMatch`, `unconfirmMatch`), app-init.js | bom-events.js |
| `LINKING_MODE` | store.js (`setLinkingMode`, `setReverseLinkingMode`) | bom-events.js, inv-events.js |
| `LINKS_CHANGED` | store.js (`addManualLink`), app-init.js | bom-events.js |
| `SAVE_AND_CLOSE` | app-init.js | bom-events.js |
| `FLYOUT_OPENED` | group-flyout/flyout-panel.js | inventory/inv-events.js |
| `FLYOUT_CLOSED` | group-flyout/flyout-panel.js | inventory/inv-events.js |
| `FLYOUT_ACTIVE_CHANGED` | group-flyout/flyout-panel.js | inventory/inv-events.js |
| `FLYOUT_SEARCH_CHANGED` | group-flyout/flyout-events.js | inventory/inv-events.js |
| `VENDORS_CHANGED` | store.js (`setVendors`) | inventory/inv-events.js |
| `PO_CHANGED` | store.js (`setPurchaseOrders`) | inventory/inv-events.js |
| `LABEL_MODE` | label-selection.js | inventory/inv-events.js, label-selection.js |
| `LABEL_SELECTION_CHANGED` | label-selection.js | label-selection.js |
| `LABEL_BULK_SELECTION` | label-selection.js | inventory/inv-events.js |

**Non-emitting setters:** `setInventory()`, `setBomResults()`, `setBomMeta()`, `setBomFootprintNearMisses()`, `setBomDirty()`, `setPreferences()`, `saveInventoryView()`, `loadLinks()`, `clearLinks()` — callers handle emission or don't need it. (`setThreshold()`/`setShortcutPrefs()` propagate via `preferencesSignal`, not EventBus — see the Signals rule below.)

**Change-only emitters:** `setVendors()`/`setPurchaseOrders()` emit `VENDORS_CHANGED`/`PO_CHANGED` **only when the data actually differs**. `onInventoryUpdated()` re-fetches both after *every* inventory mutation — including ones that cannot touch them, e.g. the `record_fetched_prices` write a hover tooltip performs — so an unconditional emit turns a passive hover into a "the user changed a PO" signal, and `js/panel-collapse.js` answers that by force-reopening the collapsed Purchase Import panel. Guarded by `tests/js/panel-reopen-noop-refresh.test.js` (which also forces every new `REOPEN_TRIGGERS` entry to be classified refresh-fed vs one-shot) and `tests/js/e2e/panel-collapse-passive.spec.mjs`. Any future refresh-fed `*_CHANGED` event needs the same treatment.

**Signals vs EventBus:** preferences propagate via `preferencesSignal` in store.js (see `js/signals.js`), not EventBus. Rule: new cross-panel *state* uses signals; EventBus remains for discrete UI *events*.

## Key Policies

- **Error policy**: prefer `AppLog.warn`/`AppLog.error` over silent catches. Throw errors rather than silently failing.
- **Test policy**: never use `pytest.skip`, `pytest.importorskip`, or `@pytest.mark.skip` to hide missing dependencies — add them to `requirements-dev.txt` instead. Tests must run, not be skipped.
- **UI clipping tests**: `tests/js/e2e/sticky-buttons.spec.mjs` and `tests/js/e2e/resize-visibility.spec.mjs` verify that action buttons (Adjust, Confirm, Link) are not clipped by panel overflow. Never weaken these tests (e.g., by relaxing tolerances, removing viewport sizes, or switching from individual-button checks to cell-level checks). If a CSS change causes these tests to fail, fix the CSS — the test is catching a real bug.

### Traps

- **WebView2 caches JS:** editing JS and relaunching shows stale code. The app uses a persistent WebView2 profile by default (gated by the `DUBIS_WEBVIEW_PROFILE` check in `app.pyw`). Force fresh behavior: `DUBIS_WEBVIEW_PROFILE=ephemeral python app.pyw`. The profile is single-owner, like the data dir: a second, attached window runs ephemeral on purpose, since WebView2 locks its UserDataFolder per process and the self-heal path *deletes* the folder — a shared one would let the second window wipe the first's live profile. The origin is now `http://127.0.0.1:<port>` (the `/v1` server's loopback port), not `file://` — the profile cache keys on origin, so this trap and its fix are unchanged, just served over HTTP instead of the filesystem.
- **pywebview second-origin navigation race:** don't navigate a freshly-created pywebview window to a second origin too early (e.g. from Python, right after window creation, before the target server is confirmed up) — it corrupts the JS-bridge callback wiring (symptom: `JavascriptException: <callback> is not a function` on later `evaluate_js`/bridge calls, even though the page itself loads fine). Fixed by having `splash.html` self-navigate (JS-side `location.href` change) only after its own poll confirms `/v1/health`, with a bisected minimum first-poll delay of ≥500ms before that first poll — bisection data lives in `.superpowers/sdd/task-8-report.md`. If you ever see bridge callbacks silently stop working after a window navigation, suspect this race before anything else.
- **Backend change → regenerate fixtures:** after changing Python inventory/columns/prices logic, run `python scripts/generate-test-fixtures.py` or vitest fails with confusing value mismatches. Easiest: just run `bash scripts/verify.sh` (see Testing & Linting).
- **Inventory record field change:** if you add, remove, or rename a field in the inventory record (the dict that `cache_db.query_inventory` sends to JS), edit `domain/schema.py` first, then run `python scripts/gen-inventory-types.py` to update `js/inventory-record.d.ts`. If you forget, `npx tsc --noEmit` (run by CI and verify.sh) will fail with "inventory-record.d.ts is stale".
- **Don't import `js/constants.js` in test setup:** it has a top-level `await fetch` at line 3 that crashes vitest collection; keep `js/ui-helpers.js` store-free and use lazy imports in tests instead.
- **Visual bugs need pixel-truth tests:** geometry-asserts-itself property tests can pass while the visual bug persists. See `docs/visual-testing.md`.
- **Root zoom splits the page into two px spaces:** `html { zoom: var(--ui-zoom) }` (js/ui-zoom.js) means `getBoundingClientRect()`, `event.clientX` and `window.innerWidth` report *post-zoom* px, while `offsetWidth`, `documentElement.clientWidth` and any px you *write* to a style are *authored* px. Mixing them displaces an element by exactly the zoom factor — and looks flawless at 100%, where the two spaces coincide, so it survives any test written without zoom in mind. Positioning code must work entirely in authored px: rects from `innerRect()`, window bounds from `zoomedViewport()`, pointer deltas through `toInnerPx()`. `tests/js/zoom-geometry-guard.test.js` enforces this across all of `js/`.
- **Never author bare `vh`/`vw`:** viewport units resolve against the viewport and are *then* scaled by the root zoom, so `max-height: 80vh` becomes 160% of the window at 200% zoom (modal spills off-screen, its buttons unreachable). Use `calc(80 * var(--vh))` / `var(--vw)` from `css/tokens/scale.css`, which divide the zoom back out, and `height: 100%` for full-height layout.
- **A cart line prices only from a recorded quote:** `GET /v1/carts/{id}/plan` reads `events/price_observations.csv` and invents nothing, so a part nothing has quoted plans as unpriced — correctly, but it looks like the planner is broken. Two halves of the same mistake have already been fixed and are easy to reintroduce: `record_fetched_prices` must record a quote for a part that is **not** in inventory (a BOM turns up nothing else, and the write used to drop it and still answer 200), and `_offers` must consult distributors that merely *quoted* the part, not just `get_sourced_distributors`, which only knows the `parts` table and the purchase ledger. The `prices` cache table still skips unknown parts — its `part_id` has an FK into `parts` — which is why the CSV, not the cache, is the planner's input. Seed a whole BOM with `scripts/seed-bom-prices.py`.
- **`data/` means two different directories:** on the desktop the static root *is* the repo, so `<img src="data/lcsc-icon.ico">` and the backend's data dir are the same folder and everything resolves. The container deployment (`fremont`) serves the image root (/app) and keeps user data on a PVC (/data), so a *frontend* asset under `data/` (the four distributor icons, the browser-tab icon) only resolves if the Dockerfile copies it into the image **and** `.dockerignore` exempts it from the blanket `data/**` exclusion — an unexempted file is missing from the build *context*, so its COPY fails the build outright rather than producing an image without it. `tests/python/test_container_assets.py` fails on either half drifting. Anything that genuinely lives in the *user's* data dir can never be a static URL at all: a fetched vendor favicon (`sources/favicons/<hash>.png`) has to travel as the `favicon_data_uri` that `/v1/vendors` already returns, which is what `vendorIconFor` in `js/ui-helpers.js` prefers. Both halves look flawless on the desktop app and 404 on every remote client. Same trap, server side: `server/routes/openpnp.py` reads its family table from the image root, not the data dir, and answers a missing file with `{}`, so an uncopied asset degrades silently instead of erroring.
- **The PyInstaller bundle ships only what someone hand-listed:** same trap as above, third packaging system. `dubIS.spec`'s `datas` is an enumeration, so an asset added to the repo is *absent from the bundle by default* and running from source can never notice — from source every path resolves to the repo itself. Eight tracked assets went missing that way at once, two fatally: `data/constants.json`, which `inventory_api.py` reads at *import* time — the built app died with `FileNotFoundError` before it even imported `webview`, and `js/constants.js` line 4 *throws* on a 404 of the same file, so the frontend would have died too — and `splash.html`, which is the window's first paint. `tests/python/test_pyinstaller_spec.py` now guards both directions — a listed path must be tracked in git (or the build aborts on a clean clone), and a path the app demands must be listed. It derives the demand three ways, because no one scan sees everything: frontend static URLs, `ast`-traced Python reads rooted at `__file__`/`APP_DIR`, and *every tracked file under `data/`* — that last one is the default-flip, and the only reason it catches `data/pnp_part_map.json`, whose root arrives as a function parameter no static scan can follow. A new tracked `data/` file is now a decision: bundle it, or name it in `_NOT_BUNDLED` with a reason. Second half of the same trap: bundled assets live under `sys._MEIPASS`, **not** `dirname(sys.executable)` — PyInstaller 6 puts a onedir payload in an _internal subdirectory beside the launcher, and a macOS .app keeps the launcher in Contents/MacOS with the payload in Contents/Frameworks, so resolving `APP_DIR` off the executable points every asset at a directory holding nothing but the launcher. A complete bundle still reaches no first paint. What the guard cannot see: anything fetched by a runtime-built URL string, any asset outside `data/` and outside the HTML entry documents, and whether the bundle actually *runs* — nothing in CI builds the spec.
- **A desktop-only dependency escapes a narrow `except`:** the pattern has bitten twice, both times as a 500 on a route the frontend calls at *every* startup. `import winreg` raised `ModuleNotFoundError` past an `except OSError`; DigiKey's hidden pywebview window raises `WebViewException` — a plain `Exception` — past `validate_session`'s `except (RuntimeError, OSError)`, 35 seconds late, because with no GUI loop `webview.create_window` returns a Window nothing ever initializes and `load_url` blocks 20s before giving up. The fix is never a wider `except`: it is an availability predicate callers branch on, in the shape of `browser_page.available()` — `digikey_session.cdp_login_available()` (is this Windows) and `digikey_client.hidden_window_available()` (is there a GUI loop). Note that the *phantom* window is not harmless: it lands in the process-wide `webview.windows`, which is exactly what both `hidden_window_available()` and `browser_page.available()` read, so letting one be created makes both of them lie afterwards — which is why `_ensure_window` refuses instead of catching. When a probe cannot run, the honest answer is inconclusive, never expired: `validate_session` returns the session unchanged rather than invalidating cookies it could not check.
- **Header additions can push the panels off-screen:** `.header` is `flex-wrap: wrap`, so a new control adds a whole ~28px row at narrow widths and shifts every panel down — enough to shove the Import button off an 800×600 viewport. `tests/js/e2e/resize-visibility.spec.mjs` catches it; the fix is a `max-width: 1199px` media query hiding the control below the app's documented 1200×700 minimum (see `css/components/ui-zoom.css`), not loosening that spec. A control that cannot be hidden goes in its own row *below* `.header` (see `css/components/server-tabs.css`) and must not wrap either — scroll horizontally instead, or N servers become N rows and the trap reappears one element lower.
- **A scrollable child of a flex column absorbs the whole overflow and vanishes:** `overflow-y: auto` sets a flex item's automatic minimum size to 0 instead of its content height, so in a `max-height`-capped `flex-direction: column` box it is the *only* item that can shrink — every `overflow: visible` sibling keeps `min-height: auto` and gives no ground. The entire deficit therefore lands on the one scroll pane, which collapses to **0px** while its children stay in the DOM at full width. That is what emptied the Preferences category-colour sliders (`.prefs-sliders` inside `.prefs-modal-wide`, `css/modals.css`): a section heading with nothing under it, no console error, and the pre-existing test measuring each row's left/right edges still green because a 0px-tall row has perfectly good left and right edges. Growing the modal is what trips it, so it reads as "whatever I added last broke it" — the sliders went missing when the server picker and tab strip were added, and looked source-specific. Fix: `flex-shrink: 0` on the scroll pane and let the modal (which already sets `overflow-y: auto`) be the scroll container — never a wider `max-height`. Guarded by the height assertions in `tests/js/e2e/resize-visibility.spec.mjs`; any new scroll pane inside a flex-column modal needs the same pair.

## Common Workflows

### After modifying Python backend code
```bash
python scripts/generate-test-fixtures.py   # regenerate JS test fixtures
npx vitest run                              # verify JS tests still pass
pytest tests/python/ -v                     # verify Python tests still pass
```
JS tests use pre-generated JSON fixtures derived from Python backend logic. If you change how inventory loads, how columns are detected, or how prices/distributors work, the fixtures go stale and JS tests fail with confusing mismatches.

If you change the inventory record shape (add/remove/rename a field in `cache_db.query_inventory`):
```bash
# 1. Edit domain/schema.py to match the new field
```

### After modifying distributor clients or normalizers
Three markers, all deselected by default, so plain `pytest` never collects any of them. `live` means "hits a real endpoint"; `browser` and `credentials` qualify a `live` test by naming what else it needs, and never appear on their own. Run them locally before merging changes to `digikey_client.py`, `lcsc_client.py`, `mouser_client.py`, `pololu_client.py`, `jlcpcb_client.py`, `browser_page.py`, the normalizers, or `scripts/capture-distributor-fixtures.py`:
```bash
pytest -m live           # everything: network + the shared browser + local credentials
                         # (cached DigiKey cookies in data/digikey_cookies.json,
                         #  Mouser API key in data/mouser_credentials.json)
pytest -m browser        # only the shared-browser ones; needs DUBIS_CDP_URL
```
A missing credential — and an unset `DUBIS_CDP_URL` in a `browser` run — causes a test failure with an actionable message, not a skip. The marker is the opt-in; once a test is selected, missing configuration is a failure, because a green skip would report success for a fetch that never happened.

The Mouser API key is optional **for the app**: without one, `mouser_client` renders the product page in a browser (`browser_page.py`) and parses `table.pricing-table`, which is where the per-carrier ladders and the MouseReel fee come from. That path used to be untestable, since pytest has no GUI event loop — but `browser_page` can now attach over CDP to a browser running elsewhere, so `DUBIS_CDP_URL=http://browser-x.browser.svc.cluster.local:9222 pytest -m browser` exercises it from anywhere that can reach the cluster's shared Chrome. Keep the API key configured as well, or the Mouser half of `pytest -m live` proves nothing.

**Nothing in CI speaks CDP.** The advisory `distributors` job in `.github/workflows/ci.yml` runs `-m "live and not credentials and not browser"` — LCSC and Pololu, which need only a network. Giving a runner CDP would mean labelling `arc-runners` `browser-client=enabled`, and CDP is unauthenticated, so that label lets any pushed branch read the cookies of a browser holding live logged-in sessions; Isaac declined it. Upstream Mouser drift is watched a different way, below. Full reasoning: `docs/ci-reference.md`.

If live runs reveal upstream drift, refresh the committed fixtures and commit the result:
```bash
python scripts/capture-distributor-fixtures.py
git add tests/fixtures/generated/distributor-scrapes.json
```
The fixture holds five blocks, not four: Mouser is captured twice, as `mouser` (Search API JSON, needs a key) and `mouser_product` (the normalized product a *deployed* dubIS server returns — that server has a browser, so this is how the per-carrier ladders get captured without CI touching one). The credential-free blocks (LCSC, Pololu, `mouser_product`) self-refresh weekly via the scheduled `.github/workflows/refresh-fixtures.yml` workflow, which opens a PR. `mouser` and `digikey` are local-only (refresh them via `pytest -m live`); their credentials never run on CI.

Mind what each half proves. `mouser_product` records what **upstream** returns, as parsed by whatever the deployed server runs — the right instrument for "has Mouser changed its page", the wrong one for "does this branch still parse it". The branch's parsing is covered by the hand-written page tests in `tests/python/test_clients_mouser.py` and, wherever a browser is reachable, by `pytest -m browser`.

## Remote deployment (Phase 1c)

The `/v1` server can also run as an always-on remote instance on the k3s cluster (tailnet) — the `fremont` deployment — instead of (or alongside) the desktop app spawning it locally.

- **Auth** (`server/auth.py`): off by default (`DUBIS_AUTH_MODE=off`, today's loopback behavior, byte-identical). `on` mode resolves identity per request: **Unix-socket peer → that user's username** (see the next bullet); loopback peer → `local`; `Authorization: Bearer <token>` or `Authorization: Token <token>` (both resolve identically) matching `DUBIS_TOKENS` (`name:token,...`); the `POST /v1/auth/session` cookie; `Tailscale-User-Login` header when `DUBIS_TRUST_TAILSCALE_HEADER=1`, the request's peer IP is in `DUBIS_TRUSTED_PROXY_IPS` (the tailscale operator proxy's pod IP/CIDR — anything else, e.g. another in-cluster pod hitting the ClusterIP directly, can't forge this header), and the login is in `DUBIS_TAILNET_ALLOWLIST`. Fail-safe: trust=1 with `DUBIS_TRUSTED_PROXY_IPS` unset/empty ignores the header entirely (one warning logged, no crash). Non-local identity gets suffixed into mutation `source` (e.g. `mcp@ci`). `/v1/import/parse` (reads server-local files) is loopback-only regardless of auth mode.
- **Unix-socket identity** (`server/peercred.py`, `server/uds.py`): `python -m server --uds <path>` binds a Unix domain socket instead of a TCP port, and every request over it is attributed to the *connecting user* via the kernel's `SO_PEERCRED` uid → `pwd.getpwuid`. That is the answer to a shared Linux box: teammates reach the server with `ssh -L <port>:<path>`, sshd connects to the socket as **them**, and each person's mutations are stamped `source@<their username>` instead of every session collapsing into `local`. Unforgeable (the uid comes from the OS, not the wire) and secret-free (no token to distribute or leak). `--uds` and `--host`/`--port` are mutually exclusive and saying both is exit 2, never a silent preference. **Traps:** (a) `request.client` is `None` for *every* UDS connection — uvicorn only fills it from a `(host, port)` peername — so the peer-credential branch must sit FIRST in `_resolve()` or every request 401s and the feature reads as a broken server; (b) the socket is not in the ASGI scope at all (verified against uvicorn 0.52.4's two scope literals), which is why this is a `uvicorn.Config(http=...)` protocol subclass rewriting its per-connection `app_state` rather than middleware; (c) `SO_PEERCRED` is Linux-only, so `peercred.available()` is the house availability predicate (`browser_page.available()` shape) and macOS/Windows degrade to `local` — same trust class as loopback, one loud startup warning, never a raise and never a 401; (d) a uid with no passwd entry resolves to `uid:<n>`, which still separates two callers, rather than to a shared name; (e) on Linux `SO_PEERCRED` against a TCP socket returns a *zeroed* struct that reads as uid 0 (root), so the AF_UNIX family check, `SO_DOMAIN`, and a `pid > 0` check all gate it; (f) a *named* peer is not `local`, so `require_loopback` refuses them `/v1/import/parse`'s server-local `path` branch — deliberate, since the server may run as a different account than the caller, and the `file_b64` branch stays open. uvicorn leaves the socket file behind and a SIGTERM skips atexit entirely, so `uds.prepare_socket_path` (connect-probe, then unlink only a stale *socket*) is what makes `--uds` restartable. `tests/python/server/test_peercred.py`, `tests/python/server/test_main_transport.py`.
- **Deploy**: container image is `Dockerfile` (repo root) + `deploy/` (kustomize: namespace/deployment/service/ingress/pvc/argocd-application). CI (`.github/workflows/build-image.yml`) builds+pushes `ghcr.io/dubnubdubnub/fremont:<full-sha>` on merges to `main` (build+push only — no git write-back, since `main` is PR-protected; the built sha is printed to the job summary and pinned manually in `deploy/kustomization.yaml`, or via Argo Image Updater later). The PVC `dubis-server-data` and Secret `dubis-server-auth` keep their pre-rename names on purpose — renaming either orphans the data or the tokens. Full step-by-step: `docs/deploy-runbook.md`.
- **Which server the desktop shows**: set `DUBIS_URL` env or `data/preferences.json`'s `server_url` to point the desktop app at an already-deployed remote server such as `fremont`. This is no longer a launch *mode*: `app.pyw` always boots its own local `/v1` server (the hub) and the window always opens on `splash.html?port=<local port>`, so the resolved URL only seeds which *source* the hub starts active on — `remote_mode.resolve_remote_base_url` keeps its precedence (env > pref > local), `app_launch.seed_initial_active_source` hands it to `server/sources.py`, and switching servers needs no restart. `tools/dubis-cli` picks up `DUBIS_TOKEN` for its bearer header the same way.
- **A second window attaches; it does not start a second hub**: `.dubis_lock` guards one writer to the local data dir, not one window. `app.pyw` probes the lock before creating its window (`app_launch.resolve_launch` — acquire-and-release, because only the OS can say whether a holder is *live*; a crashed run leaves stale pid/port bytes behind). Free → this process boots the hub and owns it. Held by a live hub that answers `/v1/health` → **attached mode**: no boot thread, no lock, no PnP server (that port is machine-wide and the owner has it), no mirror push, an *ephemeral* WebView2 profile, and a splash pointed at the owner's port. `_cleanup` returns early for an attached window so closing the second window can't tear the hub out from under the first. Held but not answering → a dialog naming the pid, and no window. An attached window polls the owner and, when it goes, says so (`app_launch.OWNER_GONE_MESSAGE`) rather than silently 500ing every action — there is no reconnect, because the hub held the lock and the honest move is "open dubIS again".
- **Server picker + tab strip**: Preferences keeps a roster of servers in `data/preferences.json`'s `servers` (`[{id, name, url}]`); the strip under the header opens **tabs** over them. A tab is a view *instance*, not a server: it has its own id, its own `sources` array (one id, or several for a group) and its own inventory view snapshot, so the same server can be open twice with different filters. `All` is not a concept — it is a group whose source set happens to be every source, and `activeSourceValue` still serializes that to the hub's `merged` token, so retiring it needed no wire change; any other subset serializes to the comma-joined set `X-Dubis-Source` accepts. Persisted as `server_tabs` + `active_tab` + `active_source` in preferences. Decisions live in `js/server-tabs-logic.js` (tab order, labels, dot claims, close/move/group/selection rules, the drop target), DOM in `js/server-tabs.js`, styling in `css/components/server-tabs.css`. Per-tab view state reuses `captureView`/`applyView` from `js/inventory/saved-views.js` rather than a parallel snapshot. Which tab is in front rides `activeSourceSignal` (js/signals.js), not EventBus — cross-panel state two panels render. **Traps:** (a) `server_tabs`/`active_tab`/`active_source` are preference keys, so they must stay in `loadPreferences()`'s explicit carry-through or they silently read back as defaults; (b) the strip lives in its OWN row *below* `.header` and hides under `max-width: 1199px`, because a control inside `.header` trips the wrap trap above, and it must never wrap — N tabs are one row plus a horizontal scroll; (c) the drag is native HTML5 DnD and writes no px anywhere, and `dropTarget()` is handed `toInnerPx(clientX)` against `innerRect(el)` so both sides of the comparison are authored px (see the root-zoom trap); (d) `+` opens a **menu** of servers (`newTabChoices`) rather than duplicating the front tab, and that menu is parented to `document.body`, because the strip is `overflow-x: auto; overflow-y: hidden` and would clip a child dropdown to its own height — which is why it is the one thing in `js/server-tabs.js` that writes px, in authored space via `innerRect`/`zoomedViewport` like `js/text-popover.js`.
- **Every window names its own source**: `server/dispatch.py` keeps NO mutable "current server" — a `/v1` request is served from `X-Dubis-Source`, and one without it falls back to the *persisted default*, which is whatever window saved it last. Several windows are open on different servers on purpose (a second window attaches to the first's hub), so **a dubIS window must send the header on every request, including the first of a page load**. `js/api.js` does it for all of them through `setSourceHeaderProvider`, which `js/store.js` installs at import time; it returns `""` until preferences load, and the only request in that window is `load_preferences`, whose route is local-only and never proxied. `apiOn(sourceId, ...)` overrides it per call to route a write in a merged view. **Because the header is always present, a refusal keyed on it alone hits the window, not a stray caller**: `merged` (and any tab group) has no answer on a route other than `GET /v1/parts`, but only a *write* there is 400ed — a **read** falls back to the hub. Keying that refusal on "the selector came from a header" instead of "the request writes" is what made a window on the All tab 400 five of its startup reads (vendors, purchase-orders, warnings, generic-parts, the DigiKey session), one red toast each; see `Registry.resolve` in `server/sources.py`. Consequences: switching a tab is a LOCAL move (the next request simply asks for something else), `PUT /v1/sources/active` only saves the default and publishes no SSE, and the switching window therefore drives its own `scheduleInventoryRefresh()` — nothing announces the change to other windows, which is the point. **What triggers that refresh is `syncShownSource` in `js/store.js`, which compares the tab set's serialized selector against the one the rows on screen were fetched with — never `persistTabs()`'s "did the saved default change".** The two look interchangeable and are not: closing the front tab (and grouping, and a roster edit that deletes a tab's server) publishes TWICE — once for the new tab set, once for the switch that follows — so the first publish records the new default and the second truthfully reports nothing changed, and the grid was left showing the closed tab's rows. `publishTabs` is the single place both the persist and the refresh decision hang off. A set is merged in roster order, not the order named, so reordering tabs cannot change which server wins a metadata conflict.
- **Server picker mechanics**: `js/servers-logic.js` holds every roster decision (validation, the add/edit/remove transforms, and what each row's dot may claim), `js/server-probe.js` does the cross-origin `GET /v1/health`, `js/server-list.js` renders the rows and polls only while the modal is open. Selecting a row switches live — it activates the tab already showing that server, or opens one; `client_shell.restart_app` is still on the frozen surface but nothing in the picker calls it. A dot means *reachable from this window*, which is why that probe runs in the browser; the strip's dots mean *reachable from the hub*, which is the honest question now that the hub does the fetching. Both vocabularies obey one rule: unprobed reads *unknown*, never red. Two picker rows can't be probed at all — the Local row while this window is remote, and an `http://` target on an `https` page (mixed content). `/v1/health` carries `Access-Control-Allow-Origin: *` so the probe can read it; it is the only route with a *wildcard*, and `tests/python/server/test_health_cors.py` enumerates the whole cross-origin surface (health's `*`, the two JLC intake routes' one-extension preflight, nothing anywhere else) and fails if it spreads.
- **Authenticating to a source: the token never touches the browser**: a remote server running `DUBIS_AUTH_MODE=on` needs a bearer token, and the *hub* is what sends it — `server/sources.py`'s `SourceClients` pools one `httpx.AsyncClient` per `(url, token)` and puts `Authorization: Bearer <token>` in its **default** headers, so no outbound call site can forget it. The browser is same-origin to its own hub and never talks to a source at all, so it needs no credential: `js/api.js` correctly sets no `Authorization` header, and the `POST /v1/auth/session` cookie bootstrap is for a browser pointed *directly* at a remote dubIS, not for the desktop client. The token lives in `<data_dir>/server_tokens.json` (`server/token_store.py`), keyed by source id, `0600`, gitignored as `data/server_tokens.json*` (the `*` covers the atomic-write `.tmp`) — **not** in `data/preferences.json`, because `GET /v1/preferences` hands that whole file to the page and `js/store.js` posts it back through a `normalizeServers` that knows only `{id, name, url}`: a token there was both console-readable and *erased by the next save of any unrelated preference*. `/v1/sources` is its only writer (`POST`/`PATCH` take `token`, write-only); `GET /v1/sources` answers `has_token` and never the value; `/v1/preferences` strips the key in both directions and migrates a legacy one out on the next registry read. `DUBIS_TOKEN` seeds the synthetic source a `DUBIS_URL` launch conjures (`app_launch.seed_initial_active_source(url, token=...)` → `_boot_default_token`), held in process for the same reason `DUBIS_URL` is: `app_restart.py` strips both, so a one-off override cannot outlive its session.
- **A green reachability dot cannot mean "this will work"**: `/v1/health` is in `server/auth.py`'s `EXEMPT_PATHS`, so a source whose auth we cannot satisfy answers the probe *cheerfully* while 401ing every request that carries data — the worst failure shape there is, because the dot the user checks says fine. `server/sources.py`'s `probe` therefore makes a **second** request, to a deliberately non-exempt route (`AUTH_PROBE_PATH = /v1/meta`), and returns a `ProbeResult` whose `auth` is `ok` / `required` (401, no token held — the user must supply one) / `rejected` (401 with a token — it is wrong or expired) / `unknown` (unreachable, or the auth leg itself failed). Only 401 is read as an auth answer: a 404 from an older dubIS without `/v1/meta`, or a 500, means the middleware let us through and must not paint a "needs a token" warning on a server that needs none. `GET /v1/sources` carries `auth` beside `reachable`, and the picker renders it as the row's credential chip — the only way the user learns a credential is missing, since no probe of an exempt route ever could.
- **`ssh://` sources: the hub owns the tunnel** (`server/ssh_tunnel.py`, onboarding in `docs/ssh-sources.md`): a roster URL `ssh://[user@]host[:sshport]/<target>` — target a remote socket path (e.g. /run/dubis/dubis.sock, preferred, so `server/peercred.py` attributes each teammate as themselves) or, when it contains a `:`, a remote TCP `host:port` — makes the hub spawn the system `ssh -N -L 127.0.0.1:<ephemeral>:<target>` (BatchMode, ExitOnForwardFailure, ServerAlive 15x3, `StrictHostKeyChecking=accept-new`, ControlMaster off) lazily on first use. `SourceClients` gives that source an httpx client whose transport (`TunnelTransport`) ensures the tunnel and rewrites each request onto its loopback port, so proxy, fan-out and probe need no ssh awareness; a `TunnelError` is an `httpx.TransportError`, so it travels the "unreachable" path everywhere with ssh's stderr turned into the reason (`kind`: auth / host_key / dns / unreachable / remote_target / timeout / no_ssh / exited). A tunnel that dies restarts on next use (same port when free); a failed start backs off 1s→30s. `GET /v1/sources` carries `tunnel` and puts the sentence in `detail`; the picker cannot probe an ssh URL from the browser, so `probePlan` answers `hub` and the dot is `hubDot` of the hub's answer — unknown until it has one, never red. Both URL validators (`parse_ssh_url`, `parseSshUrl`) are pinned by one case table, `tests/fixtures/ssh/url-cases.json`. **Traps:** (a) Linux `PR_SET_PDEATHSIG` fires when the forking *thread* exits, and `ensure()` runs on anyio worker threads that idle out, so a naive `preexec_fn` kills a healthy tunnel seconds after it comes up — every spawn goes through `_spawn`'s one long-lived thread; (b) ssh binds the local `-L` listener only after authentication, so "port accepts" is the readiness signal, but a missing *remote* target only shows up per connection as an `open failed` stderr line — `explain()` re-reads stderr after a transport error and reports `remote_target` while `state` stays `up`; (c) cleanup is lifespan + `atexit` + a `<data_dir>/.ssh_tunnels.json` pidfile reaped on the next start (pid **and** exact `-L` spec must match), since SIGKILL skips the first two and macOS has no PDEATHSIG. An attached second window has no hub and spawns nothing.
- **Container feature gaps**: the container image is desktop-feature-limited by design — no DigiKey WebView2/CDP scraping, no OS file dialogs, no OCR (tesseract not installed). Keyless Mouser fetching is no longer on that list: the image still has no browser, but `DUBIS_CDP_URL` (set in `deploy/deployment.yaml`) points `browser_page` at the cluster's shared Chrome over CDP, so `browser_page.available()` is true in-cluster and the product page renders. That requires the `dubis` namespace to carry `browser-client=enabled`, which it does; without the label the fetch falls back to the urllib scrape Mouser blocks, and a Mouser API key is the alternative. Those API methods already fail with typed errors when their dependency is unavailable; this is documented, not a bug to fix in-container.
- **A pushed JLC credential lands on the local hub, never on the server you are looking at**: `POST /v1/distributors/jlcpcb/pairing` and `POST /v1/distributors/jlcpcb/session` are both in `proxy.LOCAL_ONLY_PATHS` *and* call `auth.require_loopback` (threat-model rule 5 — a hub must never forward a credential upstream), so a deployed `fremont` can never be paired from a laptop: in `DUBIS_AUTH_MODE=on` a token- or tailnet-identified caller is not `local` and gets 403 `loopback_only`. Mind the deliberate asymmetry — the *read* routes are not local-only, so `/v1/distributors/jlcpcb/sessions` and `/v1/distributors/jlcpcb/library` are served by the **active source**. Pair while a remote tab is in front and the write goes to your hub while the panel keeps reading the remote's empty store and says "No JLC account paired"; pair from a Local tab. Remote JLC credentials are out of scope on purpose, and `require_loopback` is a *no-op* in auth-`off` mode (no middleware, so no identity to reject — same trust model as `/v1/import/parse`), so the gate is only real where auth is `on`. Reasoning, the three things a user loses, and what a deliberate exception would cost: `docs/plans/2026-09-20-extension-credential-capture.md`. **The extension's POST is cross-origin and preflights** — its `host_permissions` names jlcpcb.com only, and Chrome match patterns cannot name a port, so widening it would mean granting fetch + cookie-read for every loopback service. Instead the two intake routes answer the preflight for exactly the pinned `chrome-extension://` id (`BRIDGE_EXTENSION_ID` in `server/routes/distributors.py`), including `Access-Control-Allow-Private-Network: true`, which Chrome checks *before* the CORS result for any request into loopback; every other origin gets a bare 403. That id is *derived from `extension/jlc-bridge/manifest.json`'s `key`* by `tests/python/test_extension_manifest.py`, because a drift between the two fails silently in the browser with no server-side trace. CORS restrains browsers, not clients, so `require_loopback` and the nonce are still the whole gate. **Every response from those two paths carries the grant, errors included** — `BridgeCorsMiddleware` (same module, registered *last* in `server/app.py` so it is outermost) stamps it in the ASGI layer, because the handler-level version it replaced wrote onto FastAPI's injected `Response` and so was lost on every raise: an expired nonce's 401 reached the extension as "Failed to fetch", which with a 10-minute TTL is the error users hit most. Decided, not incidental: those bodies are an error string, a code and an optional detail — no credential, no inventory data — and only the pinned id ever gets the header. Consequence to know: the `403 loopback_only` — and, in auth-`on`, a `401` from `AuthMiddleware`, which the outermost position wraps — carry it too when the Origin matches; both bodies are fixed constants, and CORS changes readability, not reachability, so the gate is unchanged and only the header is. Two smaller traps live here as well: the two path strings exist in four places (route decorators, `INTAKE_PATHS`, `proxy.LOCAL_ONLY_PATHS`, the tests) and a rename that misses one breaks the handshake *silently* — `test_every_copy_of_the_two_intake_paths_agrees` is the guard; and a handler docstring on a `/v1` route is public API text (it becomes the OpenAPI `description` and the generated CLI help), so internal notes go in comments.
- **DigiKey login is Windows-only everywhere, not just in-container**: `digikey_session.find_default_browser_exe()` resolves the default browser through the Windows registry, so the launch-a-browser-with-CDP path (interactive login *and* the headless startup session probe) cannot run on macOS/Linux at all. `cdp_login_available()` is the guard — the `browser_page.available()` pattern — and `check_session` answers `{logged_in: false, supported: false, message: "…Windows-only…"}` there. It must stay a truthful dict, not a raise: the frontend calls `GET /v1/distributors/digikey/session` on *every* startup, so an exception makes every non-Windows launch log a red error and renders "Not logged in" for the wrong reason. A `winreg` import used to escape the `except OSError` as a `ModuleNotFoundError` and did exactly that (500). A session synced from a Windows machine still validates here — the guard sits *after* the cached-cookie path, deliberately.

### Property-based testing

The example suites prove the cases someone thought of. The complementary axis — state an invariant, let a generator attack it, get a *shrunk* minimal counterexample — is Hypothesis (Python) and fast-check (JS), both real dependencies per the Test policy above. Full guide, including the ranked backlog of what to cover next: `docs/property-testing.md`.

- **Shared generators, derived from the schema, not retyped.** `tests/python/strategies.py` and `tests/js/property/arbitraries.mjs` build inventory records from `domain/schema.py`'s `INVENTORY_FIELDS`, so adding a field cannot silently produce invalid generated data — it either flows through or raises naming the field. The JS half reads a generated copy of that table (`tests/js/property/inventory-schema.generated.mjs`, from `scripts/gen-property-schema.py`), guarded for staleness exactly like `js/inventory-record.d.ts`: the `property-schema` step in `scripts/verify.sh` and CI fail if it drifts.
- **Determinism is configured, not hoped for.** `tests/python/conftest.py` registers `dev` / `ci` / `nightly` Hypothesis profiles (`HYPOTHESIS_PROFILE`, defaulting to `ci` when `CI` is set); `tests/js/property/setup.mjs` does the fast-check equivalent. CI is derandomized/seeded so a red run reproduces exactly and a green one never flips; local runs are random on purpose. `deadline=None` everywhere — a per-example time limit measures the runner, not the code.
- **They run beside the example suites, never instead.** `npx vitest run --project core --project property`; Python property files are ordinary pytest files. Total added to `bash scripts/verify.sh`: ~4s. A property suite that pushes that budget gets its `max_examples` cut, not its assertions.
- **Trap — the tautological property:** an assertion that re-implements the function under test passes forever while computing the same wrong answer. Prefer differential (`cache_db.catch_up` vs a full rebuild), conservation, round-trip and metamorphic statements. Not for DOM, I/O or pixels (`docs/visual-testing.md`).
- **A counterexample gets pinned as an example.** `.hypothesis/` is local and gitignored, so it is not a regression test: fix the bug, then add the shrunk input to the example suite and name it in a comment at the fix site (see `cache_db.py`'s catch-up `set` branch and `domain/federation.py`'s `_preserve_identity`).

## Branch Workflow (for multi-Claude development)

- **Main branch** (`main`): protected, requires PR + passing CI
- **Branch naming**: `claude/<scope>-<description>` (e.g., `claude/refactor-tests`, `claude/feature-bom-export`)
- **Squash-merge** PRs to keep linear history
- **Every task starts in its own worktree** — created *before the first edit*, not after, and not only when the branch you happen to be on looks wrong:
  ```bash
  git worktree add -b claude/<scope>-<desc> .claude/worktrees/<name> origin/main
  ```
  **Why this is not optional:** the primary checkout is shared with every other concurrent Claude session in this repo. Files left uncommitted there get swept into *another session's* commit and pushed under its PR — the work is not lost, but it lands in a PR whose title and review scope have nothing to do with it, and untangling it afterwards means either rewriting a branch someone else is actively using or shipping the change under their name. Sitting on `main` in the primary checkout is the specific state that causes this, and it has already happened once.

  Enforced, not just advised: `.claude/settings.json` runs `scripts/guard-primary-checkout.sh` as a `PreToolUse` hook on Edit/Write/NotebookEdit, which refuses an edit whose target sits in the primary checkout (`git rev-parse --git-dir` equals `--git-common-dir`; a linked worktree's does not) and prints the command above. Set `DUBIS_ALLOW_MAIN_EDITS=1` to edit the shared checkout on purpose — resolving a conflict, a release chore — where a worktree would be the wrong tool. Claude Code's built-in `worktree.bgIsolation` covers only *background* sessions, which is why an ordinary interactive one needed this.
- **Never leave feature work uncommitted in the primary checkout.** If you find changes there, move them to a worktree before doing anything else — do not commit them in place to "keep them safe".
- **Coordination**: via GitHub Issues (labels: `feature`, `refactor`)
- **Before creating a PR**: ensure lint, type check, and tests pass (see Testing & Linting section above)
- **Push via `scripts/push-pr.sh`**: Always use this script to push and create PRs. It automatically detects if your branch's PR was already merged and creates a new branch if needed.
  ```bash
  bash scripts/push-pr.sh                          # PR title = last commit subject
  bash scripts/push-pr.sh --title "fix: the thing" # explicit title
  bash scripts/push-pr.sh --body "Fixes #123"      # explicit body
  ```
  If you forget and push to a merged branch directly, CI will fail with an error telling you to use this script.
- **Verify your worktree matches your task**: a worktree left over from a previous task is not a home for this one either. Reuse one only when the new work genuinely continues what that branch already does; otherwise make a new worktree per the rule above.
- **PR your work and watch CI**: When your work is complete, push your branch and create a PR. Then monitor CI (`gh pr checks <number>`) — if any checks fail, diagnose and fix the issues, push again, and keep iterating until all checks pass and the PR is ready to merge. Do not abandon a PR with failing CI.
- **Green CI is standing approval to merge your own PR.** Once every required check passes, squash-merge it (`gh pr merge <number> --squash`) and say so — do not stop to ask. This is Isaac's rule, given so a finished, verified change does not sit waiting on a round trip that adds nothing: CI *is* the review gate here, and a green PR left open is work that is done but not delivered. Scope, and it is narrow:
  - **Only a PR this session opened**, and only on a `claude/*` branch. Someone else's PR — a teammate's, or another Claude session's — is theirs to merge.
  - **Only on genuinely green.** A pending check is not a pass; a *failing* one is never overridden, and an advisory job that is red still gets read before merging rather than waved through. `BEHIND` means branch protection wants main merged in first — `gh pr update-branch`, wait for the re-run, then merge. Never `--admin`, never a force-merge: that is exactly the gate this permission delegates to.
  - **A green PR is not licence for what comes after.** Deploying, tagging a release, pinning a new image sha, or anything that reaches a machine outside this repo is a separate decision and still gets asked.

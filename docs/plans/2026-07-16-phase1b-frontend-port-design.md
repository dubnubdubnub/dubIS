# Phase 1b — Frontend Port to /v1 + Bridge Deletion — Design

**Date:** 2026-07-16
**Parent:** `docs/plans/2026-07-15-platform-architecture-design.md` (Phase 1b). Builds on Phase 1a (PR #359: /v1 layer, SSE, legacy aliases, lifecycle).
**Startup criterion (owner, 2026-07-15):** responsiveness > readiness — the window/skeleton must appear as fast as today and clicks give visible feedback; full function may lag behind a loading state. No hard ms gate.

## Scope

The desktop app becomes a browser: `app.pyw` always starts the /v1 server on a loopback port, serves the frontend from it, and the pywebview JS bridge shrinks to a ~9-method client shell (OS dialogs/window/shell actions only). All other JS→Python traffic goes over HTTP; Python→JS pushes move to SSE. `dubis_headless.py` and `tests/e2e-server.py` are deleted. Out of scope: auth/remote (1c), prefs server/client split enforcement beyond groundwork (can ride along if cheap), mirror retirement (1c).

## Architecture decisions

1. **Generated API client map (SSOT chain extended).** The frontend keeps the exact `api(method, ...args)` string-keyed convention. A new generator `scripts/gen-api-client.py` reads `docs/openapi-v1.json` (already staleness-guarded) and emits `js/api-map.js`: `{method_name: {verb, pathTemplate, pathParams: [argIndex...], queryParams, bodyParams: [name...]}}` keyed by operation_id. `js/api.js`'s `api()` looks up the map, assembles URL/body from positional args (positional order = the frozen bridge signature order, which operation_ids preserve), `fetch`es, unwraps envelopes, and preserves the exact legacy failure contract: catch → `AppLog.error` + toast + return `undefined`. Methods NOT in the map fall through to the client shim (`window.pywebview.api[method]`). Guard: `gen-api-client.py --check` wired into verify.sh; the map is committed generated code like `inventory-record.d.ts`.
   - Special cases table (hand-maintained in the generator config, not guessed): `rebuild_inventory` → `GET /v1/parts` unwrap `.inventory`; distributor `fetch_*_product` → `GET /v1/distributors/{name}/product/{code}` (name derived from method); merged ops (`get_digikey_session` serving `check_digikey_session`/`get_digikey_login_status` call sites); scalar unwraps (`{"quantity"}`, `{"groups"}`, `{"has_purchase_history"}`, `{"spec"}`, `{"match"}`) so call sites see the same shapes the bridge returned.
   - `js/inventory-modals.js:336`'s deliberate raw-bridge distributor fetch becomes a raw `fetch` to the distributor route (no toast), preserving its per-row error semantics.
2. **Two-step mutation convention inside the phase.**
   - Step 1 (port): all mutating calls go out with `?include=inventory`; `api()` unwraps `body.inventory` so call sites (`const fresh = await api(...); if (!fresh) return; onInventoryUpdated(fresh)`) keep working unchanged.
   - Step 2 (flip, before phase close): store.js opens one `EventSource('/v1/events')`; `inventory.updated` → debounced `GET /v1/parts` → `onInventoryUpdated(envelope.inventory)`; mutations drop `include` and call sites stop consuming return values (they rely on the SSE-driven refresh). The `?include=inventory` affordance is then removed from `server/mutations.py` per the 1a spec. De-dupe rule: SSE is the single re-render source; local mutation promises resolve for control flow only.
   - `scan.receiving`/`scan.received` SSE events replace the `_scanReceiving`/`_scanReceived` evaluate_js pushes (mfg-direct panel subscribes via a shared sse.js module); `inventory.consumed` replaces `_pnpConsume` (its full-inventory arg is replaced by the `inventory.updated`-triggered re-fetch). The three evaluate_js pushes in `pnp_server.py` are then deleted (the SSE dual-writes from 1a become the only path).
3. **Client shell (the surviving bridge).** New `client_shell.py` class passed as `js_api` instead of `InventoryApi`: `open_file_dialog`, `save_file_dialog`, `load_file`, `confirm_close`, `set_bom_dirty`, `start_digikey_login`, `open_source_file`, `install_tesseract`, `bench_mark`. It holds references to the webview window + the InventoryApi only where needed (dialog helpers are already standalone in `file_dialogs.py`). `tests/python/test_api_surface.py` is rewritten to freeze THIS surface (9 methods); the old 76-method freeze retires with the bridge. `whenPywebviewReady()` keeps its pattern but probes a shim method (`set_bom_dirty`); HTTP readiness is separate (server is up before the page is served, by construction).
4. **Static serving + lifecycle.** `server/app.py` mounts the app dir (index.html, js/, css/, assets) via `StaticFiles` at `/` (API routes take precedence; mount last). `app.pyw`: start server on a free loopback port (reuse `server/run.py`), poll `server.started`, `create_window(url=f"http://127.0.0.1:{port}/", js_api=client_shell)`. `DUBIS_SERVER_PORT` env var becomes an override for a fixed port (still supported). WebView2 persistent-profile handling unchanged. Startup measured with the existing `DUBIS_BENCH_OUT` harness before/after; acceptance per the responsiveness criterion (skeleton timing unchanged — it's inline in index.html and now served from loopback, one extra local round-trip).
5. **on_closing / BOM-dirty:** keep the current mechanism — `set_bom_dirty` lives on the shim, `on_closing` still reads `api._bom_dirty`-equivalent (moves to the shim object) and `evaluate_js("closeModal.open()")` still works (webview window exists regardless of bridge). No behavior change.
6. **Tests.**
   - Functional/quality Playwright: `addMockSetup`'s ~60 pywebview mocks become `page.route('**/v1/**')` HTTP fixtures (one shared route-mock helper mirroring the old mock data; `window.__apiCalls` recorder preserved by recording in the route handler). Shim methods stay as `window.pywebview.api` mocks (dialogs).
   - Live project: the `/api/{method}` Proxy shim and `tests/e2e-server.py` are deleted; live tests point at a real `python -m server --data-dir <fixture>` (started by global-setup), using `/v1` directly. `--test-source`/`--rollback-on-exit` semantics move to server flags (`python -m server --test-source ... --rollback-on-exit`) since `dubis_headless.py` is deleted; `tests/pnp-e2e/` repoints at `python -m server` + legacy `/api/*` aliases.
   - `tests/python/test_scan_session.py`'s evaluate_js-string assertions update to assert the SSE publish instead.
   - UI-clipping E2E invariants (`sticky-buttons`, `resize-visibility`) unchanged and must stay green — they're layout tests, transport-agnostic.
7. **Missing routes added in this phase:** `bench_mark` (POST /v1/bench, trivial, keeps the dev harness) — or dropped from JS if the bench harness moves fully Python-side; decide in plan (default: keep via shim instead, zero routes — it's dev-only telemetry and the shim exists anyway → **shim**). `install_tesseract` → shim (runs winget/UAC on the client machine).
8. **Port order (self-contained → entangled), one task each:** preferences/vendors modals + part-preview + labels → import panel + group-flyout → BOM panel → inventory cluster (inventory-modals, inv-inline-edit, inv-mutations, fetch-descriptions, vendor-flyout) → store.js/app-init bootstrap + SSE flip + bridge deletion last. The generated api-map makes most of this mechanical: the per-panel work is mainly the E2E mock migration and semantic diffs (envelope unwraps).

## Deletions at phase close

`js_api=InventoryApi` wiring; the 76-method bridge exposure (InventoryApi keeps the methods — /v1 calls them — but pywebview never sees the object); `whenPywebviewReady` HTTP-side uses; `tests/e2e-server.py`; `tests/js/e2e/live/setup-page.mjs` Proxy; `dubis_headless.py`; the three `evaluate_js` pushes in pnp_server.py; `?include=inventory` in server/mutations.py; `convert_xls_to_csv` (0 callers; XLS conversion stays inside `load_file`/dialog paths).

## Risks

- **Positional-args → named body params** is the subtle mapping (the bridge was positional; JSON bodies are named). The generator derives parameter order from the operation's path+body schema; a mismatch is caught by the E2E suite and a new vitest unit for `api()` URL/body assembly against the committed api-map (table-driven, one case per method class).
- **WebView2 + loopback:** SSE (EventSource) and fetch against 127.0.0.1 inside WebView2 — verify in the first lifecycle task (spike test) before mass porting; SSE fallback risk is low (plain HTTP).
- **file:// → http:// origin change:** localStorage/persistent profile keyed by origin — the WebView2 profile keeps cookies/storage per origin, so any existing localStorage is orphaned (currently trivial usage; prefs live in preferences.json). Note in migration.
- **Playwright static config** (`scripts/serve-static.mjs`) can keep serving for pure-frontend tests; live tests exercise the real server. CI job wiring should not change beyond the deleted files.
